## 当前对象与证据优先级

1. 先解释真实对象角色。IFC 接口和紧固件的类型事实、明确部件角色属性优先。有真实 DEV 装配边时，端子箱、操动机构箱、散热器等配件归宿主组成，即使带类型属性也不另建整体；没有装配边时才用当前对象名称判独立或内部组成。
2. 类型枚举、有效设备/材料/构件类别属性及显式目录/型号映射用于分类。自由文本型号（如“220kV变压器模型04_散热器”）不是类别事实，不能据此升格为设备。用途字段只在相容的对象语义内解释：主变控制是柜的服务对象，不能把柜变成主变；站用用途可细化泛变压器。
3. 泛型可在明确允许的范围细化：E-T 到 E01/E03，E16 到其子类，未分基础到设备/建筑基础；具有设施用途的墙/板、管泵按可解释的兼容映射细化。不能将所有 C 类互相覆盖。
4. 属性足够时名称只补充相容细类；明确类型与名称矛盾时保留类型、记录冲突并标候选。两个有效属性矛盾时不按字段顺序选胜者，保留待归及冲突证据。
5. 缺属性才使用对象名称；名称按复合词最长命中和独立中心词判别，排除间隔/系统定语；安装形式修饰词（例如喷淋头的边墙型、吊顶型）不充当墙体/屋面等对象中心词。型号只在显式目录映射时参与类别，不从型号字符串猜专业；兼容有限型号代号与 CT/PT 兜底。仍无依据则 U-OBJECT，不从几何猜专业。

`basis`、`classificationEvidence` 和 `conflict` 保留判据；`classificationStatus` 为 confirmed/candidate/unresolved，与 `boundaryStatus` 分开。E-T、未分基础、显式型号映射候选及冲突不能冒充已确认用途。内部件未细分类不计为整体分类失败。

## 粒度与组合

每份来源只有整体成员、待归成员、仅来源三种主去向。共同目录、父节点、同名、同模板或邻近不足以合并。平级成套需工程标识、编号名称、兼容签名；多相主变还需明确编号、单相证据，重复相别、多组身份或异常数量保留待归冲突。主变实际装配内端子箱作为组成，独立端子箱保留 E16 设备，不按名称前缀自动吞并。

分类和树模板不参与几何 seed；规则/目录修改只失效依赖域，版本权威定义见[缓存域](../../architecture/caches.md)。执行 `npm run check:engineering-catalog -- --python` 检查代码、生成文档与参考工具目录一致；名称优先的 Python 聚合台账不作为产品实体边界真值。
