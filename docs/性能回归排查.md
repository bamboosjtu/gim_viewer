# 性能回归排查

> 采样日期：2026-09-04。范围仅包括 Semantic Core v22 之后的线路/变电加载回归、缓存版本域隔离和已经确认的重复小文件读取；没有新增 IFC Worker、Spatial SQLite Cache、Compact Runtime Cache、shared Three geometry 或默认开启 Fragments Cache。

## 结论摘要

1. 线路缓存的版本域已从共享 `PARSER_VERSION` 拆为 `LINE_PARSER_VERSION=gim-line-parser-v1` 与 `SUBSTATION_PARSER_VERSION=gim-substation-parser-v22`。旧库中明确识别为线路且使用 `gim-parser-v21/v22` 的记录会迁移到线路域，变电 Semantic Core 升级不再使线路 graph、属性和 semantic pack 失效。
2. 真实 Tauri post 采样的线路 warm path 均满足：不 native extract、线路 semantic pack 命中、Worker 执行、`read_cached_entry=0`。line02 warm 可交互中位数从 5.370 s 降至 2.420 s，line03 从 3.012 s 降至 1.577 s。
3. 变电冷启动的主要回归来源不是 Spatial Core 本身，而是解压后的工程类型识别、逐条 `read_cached_entry` 以及随后 MOD/STL。substation02 post cold 的语义时刻为 57.285 s，其中 native extract 31.013 s、小文件批量物化 5.125 s、Spatial Index wall span 17.886 s；full model 仍需 834.741 s，主导阶段是 MOD/STL 535.473 s。
4. 本轮采样没有重现此前提到的 substation02 `semanticReady≈152 s`，而是得到修改前 261.312 s、修改后 57.285 s。两次采样环境和缓存状态不同，不能把单个绝对值直接视为稳定基准；阶段证据仍明确显示 152 s（或 261 s）主要来自 Spatial Core 之外的 I/O/编排。
5. substation02 warm 仍有一个已知 GLB parse failure，导致 `rawModFallbackCount=1`；这是 geometry cache/解析问题，本轮仅保留诊断，未扩大修复范围。

### bytes 与测量边界

`invokeTimed` 对 `ArrayBuffer/Uint8Array/string` 统计精确字节；普通对象不再额外 JSON stringify，避免监控本身复制大型 payload。批量读取的 `totalMs/p95/max` 是 Tauri command 的 IPC 时延；不会和业务 span 叠加成新的 wall-clock。

## 内存口径与下一步

本轮完整诊断的 `timings.memory` 为空，未拿到 JS heap；`webviewRssPeakBytes` 是外部 WebView/进程树 RSS 采样，不能当作 JS heap。post cold substation02 的 RSS 峰值约 6.55 GB，说明去掉重复小文件读取后，剩余峰值来自 IFC/Fragments/MOD 几何和渲染生命周期，不能仅凭 parser wall span 判断。

建议下一轮先用同一 Tauri 构建补齐入口 miss reason 和 substation04 修改前 warm 基线，再根据真实数据决定：

1. 若目标是缩短 substation02 full ready，优先开 MOD/STL/GLB parse failure 与几何编译专项；
2. 若只关注 semanticReady，当前批量物化和缓存域隔离已解决本轮确认的回归，不继续微调 Spatial Core；
3. 只有在独立进程拿到稳定 JS heap/RSS 后，才评估 property lazy load 或更大的缓存架构变化。
