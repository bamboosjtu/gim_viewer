# 未保留：语义缓存恢复时的 DEV 源按需合批

日期：2026-10-23。起点：`dcbfc8c`，桌面 v0.1.1。结论：**本次按需小批读取与主线程源字节复用没有改善固定窗口的设备显示或编译推进，候选实现、专属诊断及测试已全部回退。** `test-` 表示尝试过但未通过保留门槛；不是当前产品能力。

## 问题与试验范围

`DevLodRuntime.start()` 在 `currentFiles` 存在的首次解压路径使用已有源批量预取；语义缓存恢复时 `currentFiles` 为空，按 `substationEntryPaths` 建立懒读 File，每次 `arrayBuffer()` 调用 `readCachedEntry()`。目录或模板的派生缓存缺失后，Worker 就会沿 DEV/PHM/MOD 引用链反复等待主线程转发源字节。

完整派生缓存命中本应直接恢复表示，不能为解决缺失缓存而无条件预读整个工程。本次候选选择需求触发的合批，不新增整站预载和启动 gate，不修改几何、解析、缓存键、SQLite 生产逻辑、Worker 数量、计算槽或输出消费策略。

试验仅针对 B1-1 的“语义及 IFC 可恢复、DEV 模板与 catalog 均为空”场景。它不是首次冷启动，也不是完整暖启动。

## 候选技术路线（已删除）

- 在恢复路径按实际 Worker 读请求收集路径，下一事件循环轮次调用一次现有 `batchReadCachedFiles`，每批最多 64 条、同一时刻一批；不猜测 DEV 的引用关系。
- 同路径在途读取合并；以会话为边界保留最多 32 MiB 的 LRU 源字节，超过 8 MiB 的单源不保留，极小来源按至少 256 B 计入额度以限制条目数量。
- 给每个 Worker 返回独立可转移缓冲区，避免某次 transfer 分离其他消费者仍需使用的字节；批读失败或条目缺失仍走原单项入口，合法空文件保持合法。
- 高内存压力不保留副本；释放工程时拒绝排队及在途请求，丢弃迟到结果，清空保留字节。原生读取本身未增加硬中断能力。
- 不改首次冷源预取；完整目录和模板命中时不发起源请求。32 MiB 是保留源字节的计费上限，不是整个 JS 堆、IPC 在途响应或应用进程树的硬上限。

这些设计仅通过专项回归，未因此自动获得产品保留资格。

## 阶段诊断及解释边界

导出诊断的会话时长分别约 258.097 / 230.987 s，晚于固定窗口且不同步，因此下列只作问题定位，不作同窗口加速比：

- 控制侧记录 5355 次 `read_cached_entry`，候选侧记录 1253 次已完成的 `batch_read_cached_files`；候选保留的 1 次单项读取来自空间语义恢复，不能算成 DEV 回退。
- 控制 / 候选的 bounds Worker 读取跨度最大约 20.13 / 15.15 s；compile Worker 读取最大约 3.75 / 6.19 s。两类任务与完成集合不同，不能只选 bounds 的下降证明优化成功。
- primitive 生成单任务最大约 13.4 / 14.7 ms，仍远低于这些读取跨度，不支持重回 L0 精确几何计算方向。
- 进程树私有内存采样峰值约 4.237 / 4.335 GiB。采样窗口及进度不同，不能把差值全归于源缓存，亦不能声称内存改善。
- 主线程长任务计数约 1955 / 1789，累计阻塞约 99.445 / 86.987 s，最大单项约 547 / 917 ms。由于观察时长不同，累计下降不能证明可用性提升；本轮未执行固定浏览路线，也未验收帧间隔或点击 p95。

由源码可知 Worker 原本已有 64 MiB 源字节缓存、并发同路径去重及来源亲和调度。本次额外主线程缓存未命中，与已有复用已覆盖可复用读取的解释一致，但尚不能证明全部样本都无跨 Worker 复用。合批仍保留 Worker→主线程逐源往返，并新增合批定时和串行消费等待；这些是没有转化为显示收益的可能原因，不能凭当前聚合诊断确定各项贡献。
