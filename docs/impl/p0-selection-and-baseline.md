# P0：选择查询与大站基线

本轮按浏览器的实际路径推进 P0：普通选择继续只使用 L0/L1，L2 保持用户主动请求；先建立可复核的阶段记录，再保留有测量收益的局部优化。本文解释实施决策，当前数字及验收条件集中在 [性能基线](../performance.md)，未关闭问题仍在 [问题清单](../open-issues.md)。

## 为什么先缩小选择查询

选择设备时，`collectDeviceGroups` 原先从所有已加载 MOD/STL 根开始遍历，再用 occurrence、DEV 来源及装配路径筛选。渐进式加载运行时已经持有 occurrence 到当前表示根的 row；再次遍历全站不是解析身份所必需。

同一原生 substation02 场景包含 2731 个 DEV 根。对 20 个不同 DEV 来源交替执行 100 组只读查询，原全树路径和候选路径的对象 UUID 集合全部一致，集合查询 p95 从 6.4 ms 降至约 0.1 ms。保留这项改动，但只将其作为局部 CPU 查询收益：它不足以解释此前秒级的普通选择延迟，也不作为点击反馈达标的证据。

## 实现与正确性边界

- `DevLodRuntime.getLoadedRoot` 直接读取当前会话的 row，不增加第二份索引。LOD 替换后返回新根，卸载或工程切换后不返回旧根。
- 已知 occurrence 且当前根存在时，只遍历该根；DEV 来源和装配子树的原筛选逻辑继续执行。共享 DEV 的不同 occurrence 不合并。
- 无 runtime、根未加载或没有 occurrence scope 时保留原全树路径，兼容原始几何加载和模板查询。
- 该查询不触发编译、精化或加载，不改变坐标、颜色、缓存格式与选择身份。

回归覆盖同源多实例、装配子树筛选、旧路径回退、根替换、卸载及工程代次变化。测试同时断言在命中运行时根时不再遍历无关来源。

## 如何继续定位选择长尾

沿现有 `perfTimings` 有界记录增加导航、属性摘要、属性参数、几何收集、高亮提交和相机定位阶段。记录关联 SelectionRequest 身份，并保留结束时的取消与有效状态；旧工程的迟到完成不能写入新工程性能会话。没有新增独立追踪框架或每帧扫描。

这些是墙钟阶段，可能重叠；高亮提交还可能包含等待既有提交链的时间，不能相加视为 CPU、GPU 或输入到画面呈现的时间。后续以真实输入的端到端观察确定主要延迟，再选择属性投影、渲染或提交链路线，不因局部查询变快宣称普通点选已达到 100 ms。

新源码 Release 的三次真实普通选择已确认阶段记录可导出，L2 编译数保持 0；几何收集仅 0.1–0.3 ms，导航阶段为 105.4–135.0 ms。后续应分离该导航阶段的异步等待与 UI 同步，不能仅依据外层 span 就增加第二份功能树缓存：当前功能域索引已经按树根和属性映射缓存。构建指纹、观测条件与测试结果见性能基线，不把这三次操作作为 p95 验收。

## 大站调度判断

B1-1 本轮单次原生冷基线中，DEV 在 IFC 全部结束前已经推进，最终 11250 个基础表示显示、失败 0；没有复现旧的 DEV 0/0 停滞。基础表示约 419 秒、进程树私有内存约 6.13 GiB，仍超过目标。输出消费、模板准入和缓存写入均有积压，尚不能把总耗时归因于一个 compile gate。

因此本轮不扩大 Worker 池、不放宽输出预算，也不重写已经具备唤醒和 bounds 回退的队列。历史上提高 Worker 比例的未成功路线见 [独立报告](test-dev-worker-overprovision.md)；该报告明确区分历史观察与本轮默认配置诊断。

完成快照进一步区分了计算与等待：2617 个编译任务的 Worker 墙钟总量约 33.126 s、单项最大 484.4 ms，模板队列单项等待则可达 370.438 s；缓存读取最大 5.088 s，几何及目录写入队列最大 301.123 / 351.329 s。下一轮对照应先检验任务准入、缓存读写排队和输出消费，不能把这些重叠阶段相加，或未经 A/B 就宣称关闭缓存写入会加快整站。

基础表示完成时缓存落盘仍未结束，本轮关闭前仍有待写项。它不能作为完整暖启动的前置，也不能关闭 O-02。后续必须在同一构建上补齐冷暖对照，分别观察计算、模板消费、场景提交及缓存写入，不能用首屏或总计数替代 60 秒基础表示门槛。
