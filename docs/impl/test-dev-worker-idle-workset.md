# DEV 空闲计算池的浏览工作集

## 判定与边界

保留普通空闲时的 DEV Worker 缩容与按需求恢复。substation01–03 的真实来源计算池对照取得约 105–203 MiB 的固定窗口私有提交量减少；四站的目录结果、模板字节、既有表示及恢复计算均通过检查。substation04 的进程树波动较大，没有稳定私有内存降幅证据，最终一次与首控制相比增加约 6.7 MiB，不把该样本报告为稳定改善。

这项选择有代价：退役 Worker 的解析缓存消失，新来源的计算可能变慢。保留依据是中大型样本的计算工作集减少及已有表示不受影响，不声称所有样本、所有阶段无回退。策略统一按任务与结果消费状态执行，不按样本身份分支。

本轮只处理 DEV 计算池。没有改模板 LRU、IFC 源驻留、几何缓存版本或原生持久化格式；不关闭全站 6 GiB 峰值、实际输入响应和十次完整工程切换的验收项。

## 问题与实现

原实现即使目录与模板计算已经结束，也保留整组 DEV Worker 及各自的字节、文本、DEV/PHM/MOD 解析缓存。只有 critical 压力才回收空闲线程，普通浏览会一直保留初始化容量。

现在沿用现有 10 秒 watchdog 检查，在没有活动任务、排队任务和未确认结果，且持续空闲至少 30 秒时，保留最近完成任务的健康 Worker，其余终止并清除来源亲和引用。没有可用最近记录时保留一个现存 Worker。通常在空闲 30–40 秒检查到；后台计时器延迟不作为严格回收上限。没有增加新的定时器。

普通空闲缩容后，只按可执行排队需求逐步恢复，最高仍为原配置容量。暂停的自动细节及结果背压中的编译不触发增线程；范围任务与显式用户工作沿原规则推进。已有 critical 缩容/恢复策略保持原行为。未消费结果全部确认后才开始空闲窗口，取消排队也会重新建立窗口，不把“长时间没有计算进展”误认为已经空闲。

暖缓存读取与 GLTF 解析在主线程，不要求计算 Worker。`cacheConcurrency` 在普通空闲缩容时保留原配置的消费容量；high/critical 下仍按当前线程数收紧，输入预算不变。状态中的 `workerCount` 同步为实际值，`workerScheduling` 另列 `targetWorkers`、`idleMs`、`idlePoolShrinks` 和 `idleCompacted`。

主线程持有的模板、实例、材质与缓冲区不属于被终止的 Worker。原表示保持，未来编译从会话持有的授权来源恢复；来源补发后的新 Worker 读取最新不可变 File。取消、失败替换和关闭仍由原会话守卫管理，退役 Worker 的迟到消息不提交。

入口为 [计算池](../../desktop/src/services/devGeometryWorkerClient.ts)、[模板消费及就绪诊断](../../desktop/src/services/devLodRuntime.ts)；回归位于 [Worker 池测试](../../desktop/src/services/__tests__/devGeometryWorkerClient.test.ts)及[运行时测试](../../desktop/src/services/__tests__/devLodRuntime.test.ts)。

## 输入与检查装置

基线为 `93b2f2c` 的原计算池。测量入口从 Git 读取原文件，只重定位模块与 Worker 相对地址，原任务实现不变；控制与候选使用相同的当前 Worker 文件。最终候选计算池文件 SHA-256 为 `82002da26951ccf4564fe99f8adc0cf67d932e4da71ee394a6103339714ca787`，各记录另带 `baselineSha`、`workerSha` 和来源 SHA。

Windows、i7-8700（12 逻辑核）、约 64 GiB 内存，Node 22.23.1、headless Edge 156。所有运行使用独立进程/profile，逐个执行，测量时不运行构建或其他基准。没有操作日常缓存。

四个原包 SHA 与[台账](../schema/sample-corpus.md)一致，检查解包标记后，从真实 CBM 收集物理 occurrence。所有唯一物理 DEV 根都执行范围任务，再选择文件较大的 16 个及按路径均匀分布的最多 48 个，去重后执行 L0 编译。来源以不可变 File 供给真实 Worker；不覆盖原生懒读/RPC 的性能。

| 样本 | 几何来源文件数 / 字节 B | 唯一 DEV 根 | L0 记录数 | 有 GLB | 保留实例数 / 网格数 |
|---|---:|---:|---:|---:|---:|
| substation01 | 14,340 / 60,361,837 | 285 | 63 | 63 | 63 / 2461 |
| substation02 | 2975 / 4,631,259 | 976 | 64 | 38 | 231 / 2124 |
| substation03 | 6873 / 41,863,492 | 162 | 58 | 58 | 58 / 1023 |

总计 1630 个唯一物理 DEV 根、245 条 L0 记录、219 个实际 GLB。substation02 的 26 条 empty 与 17 条 partial 保留原状态和诊断，partial 不当作完整表示。实例数、根数、来源文件数和模板数分别计量。

显示检查使用实际模板放置类、真实 CBM 累积矩阵和固定单位工程矩阵，保留模板共享；没有加载 IFC 锚点或创建 WebGLRenderer。跨控制/候选按路径核对完整目录结果摘要、GLB SHA、状态和诊断；各自进程内核对空闲及恢复前后的几何/矩阵摘要与 Object3D、Geometry、Material 身份不变。不同进程生成的 UUID 和场景插入顺序不作为身份等价要求。这不是原生画面、实际 IFC 坐标或 GPU 验收。

## 私有提交量

测量使用 Windows `GetProcessMemoryInfo` 的 `PrivateUsage`，合计本次 headless Edge 及其子进程，不用 RSS、JS heap 或缓存预算替代。准备结束后及空闲约 45 秒后各取三个相隔两秒的点，以下为各窗口三点的中位数。窗口内仍有进程树波动，不称作完全稳定驻留；不是整段峰值。

控制代码固定为同一 Git 快照。下表控制来自首轮冻结运行，最终候选是在补齐暂停/背压不扩池守卫后复查；两者跨时段，不能把全部差值精确归因于某一种内部分配。普通负载路径及 Worker 实现相同，原始运行身份单列，不迁移为原生 Release 成绩。

| 样本 | 控制 MiB | 最终候选 MiB | 控制减候选 MiB |
|---|---:|---:|---:|
| substation01 | 1417.9 | 1227.2 | 190.7 |
| substation02 | 970.8 | 865.8 | 105.0 |
| substation03 | 1186.6 | 983.4 | 203.1 |
| substation04 | 844.4 | 851.1 | -6.7 |

四站候选均由 7 个 Worker 缩为 1 个，三点检查均保持 1；一个新计算仍为 1，随后两个并发计算增长到 2，不恢复无需求的全部线程。substation01–03 在守卫补齐前的四站首轮对照也分别减少 179.6、95.6、181.5 MiB，支持这些样本的局部工作集收益，但不是三次正式冷暖矩阵。

substation04 的补测全部保留：控制三次为 **844.4 / 952.0 / 937.3 MiB**；候选普通路径三次为 **836.9 / 818.6 / 839.4 MiB**，最终候选为 **851.1 MiB**。前三次候选属于补齐暂停/背压守卫前的相同普通路径，不冒充最终源码三次复测。不能选择较高的控制值来宣称稳定下降，也不将一次 -6.7 MiB 直接解释为持续泄漏。

## 恢复成本与未保留路线

初版空闲缩容后沿用整池恢复，substation01 的三个并发重算从控制约 61.6 / 69.2 / 114.7 ms 增至 216.4 / 687.5 / 379.6 ms；虽然空闲窗口减少约 197 MiB，该普通恢复方式未保留。最终改为一个请求只用一个线程，后续并发需求再增长，并重新执行四站候选。

最终路线先执行一个新计算，再执行两个并发新计算；这些请求针对已有表示的来源重新编译，用来检查缓存变冷及线程恢复，不是普通选择或已缓存模板读取。

| 样本 | 单请求旧 / 新 ms | 随后两请求旧 ms | 随后两请求新 ms |
|---|---:|---:|---:|
| substation01 | 47.3 / 98.3 | 57.8 / 55.0 | 152.4 / 332.3 |
| substation02 | 6.0 / 10.2 | 36.2 / 3.6 | 88.6 / 139.6 |
| substation03 | 17.9 / 42.2 | 9.7 / 16.1 | 8.8 / 21.1 |
| substation04 | 5.3 / 12.6 | 93.1 / 4.8 | 206.8 / 139.8 |

不同运行的来源亲和和缓存命中会影响结果，不将少量请求作为 p95。普通路径改为按需恢复后仍有冷缓存代价，已有表示的身份与缓冲区检查保持一致；未据此证明实际点击、高亮、近景或启动时延不回退。

## 释放与重复创建

每个候选另执行十次计算池新建、真实范围/编译、消费确认和取消，GLB SHA 保持一致，每轮 Worker 所有权计数回到 0。最终场景实例、模板计数回到 0，所属浏览器进程随后退出。

最终候选最后三次池取消后的进程树私有提交量为：

| 样本 | 第 8 / 9 / 10 次 MiB |
|---|---:|
| substation01 | 1318.9 / 1312.8 / 1327.9 |
| substation02 | 951.8 / 965.1 / 969.8 |
| substation03 | 1101.2 / 1110.0 / 1115.6 |
| substation04 | 946.2 / 954.1 / 968.5 |

这是计算池边界采样，采样时主线程仍保留上述测试表示与来源。它不等同于关闭整个工程后的稳定内存，也不替代十次真实工程切换或 ≤100 MiB 的完整产品门槛。

一次早期采样遇到子进程在枚举后退出（Windows error 87），整次运行按不可用退出并清理，未用 0 代替。采样器现以新快照最多重采三次，失败快照保存在成功记录的 `unavailableAttempts`；仍不可用则失败，不增加应用任务重试或超时。

## 复现与证据

在 Windows 的 `desktop/` 下，使用 Node 22、Python 标准库及 Edge：

```powershell
npx vitest run --config scripts/benchmarks/dev-worker-workset.config.ts
# 另一个终端保持 npm run dev -- --host 127.0.0.1 运行
node scripts/benchmarks/dev-worker-workset-browser.mjs substation01 baseline
node scripts/benchmarks/dev-worker-workset-browser.mjs substation01 candidate
```

逐个替换样本 ID 完成四站；样本缺失或源 SHA 不符直接失败，不跳过。原始输入清单、逐进程内存、任务状态、模板摘要、恢复结果及循环记录均在忽略目录 `output/memory-workset/`。脚本只采集，不自动判定性能验收。

最终候选记录：`substation01-candidate-2026-10-25T04-12-17-115Z.json`、`substation02-candidate-2026-10-25T04-11-13-671Z.json`、`substation03-candidate-2026-10-25T04-10-09-149Z.json`、`substation04-candidate-2026-10-25T04-09-07-381Z.json`。相应冻结控制分别为 `03-53-39-763Z`、`03-54-48-584Z`、`03-57-59-665Z`、`03-59-03-641Z`，均为 2026-10-25。完整关联与 SHA 在 `final-paired-summary.json`，早期及 substation04 的额外记录亦保留。

最终检查：

- 四站来源准备 4 项通过，无样本跳过；最终候选四站真实 Worker、全部物理根目录、219 个实际 GLB、表示保护、按需恢复及池级循环检查通过。
- 默认单元 128 文件、1111 项通过，3 项既有条件跳过。其中 Worker 池与 DEV 运行时两个文件共 49 项，包含新增的空闲窗口、来源升级、迟到结果、暂停/背压不扩池、暖消费容量和关闭后不复活回归。
- 现有真实样本套件 3 文件、11 项通过，2 项因线路解包目录缺失跳过；四个变电样本实际执行，耗时 154.45 s。
- TypeScript/Vite 构建通过，保留既有大 chunk 等告警；文档相对链接及 `git diff --check` 通过。

日志为 `unit-tests.log`、`sample-regression.log`、`build.log`。严格入口 O-09、原生 Release、完整峰值与路线验收仍单列。
