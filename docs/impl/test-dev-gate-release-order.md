# 未保留：调整 Worker 失败时的 gate 释放顺序

日期：2026-10-23。结论：**未发现所怀疑的重复派发竞态，没有证明性能收益，生产顺序改动已撤回。** 本文的 `test-` 表示该技术假设没有通过保留条件，不代表 gate 故障不存在。

最初假设：`workerFailed()` 释放共享 gate 后才从 slots 删除失败任务，释放若立即重入 `pump()`，空闲 Worker 可能重新运行失败源。曾把 slots 删除移到 gate 释放之前。

继续核对 `geometryWorkGate.ts` 后确认，`notifyAvailable()` 已使用 `queueMicrotask()` 合并唤醒。原来的 `workerFailed()` 在微任务执行前已移除失败任务；它自身调用 `pump()` 也发生在删除之后。因此这不是已复现的 bug。

补充的“外部 gate 占用 + 一个 Worker 崩溃 + 另一个空闲 Worker + 排队任务”回归，在原顺序下同样通过：失败源只派发一次，健康任务继续执行，输出消费后 queued/active/results 均归零。没有对这一无行为差异改动计算性能加速比。

目前生产代码保持原失败结算顺序。组合回归保留，用于保护真实的故障隔离边界；后续受控源升级的修改与该撤回无关。源码中的 `workerFailed()` 未因本次假设改变，新增传输协议也不改变 gate 的结算顺序。

B1-1 当前观察到的长尾有真实阶段证据：逐源读取、目录任务优先级、主线程消费及绘制。它们的诊断和已保留收益见 [受控源工作集](dev-recovery-workset.md)。本次结论不能泛化为其他任务、预算、取消或工程切换路径均无停滞风险。
