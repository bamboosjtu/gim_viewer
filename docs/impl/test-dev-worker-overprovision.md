# 未成功路线：提高 DEV Worker 比例解决大站加载长尾

结论：这条路线曾尝试，未取得足以保留的性能收益，已回退。当前继续采用按逻辑核约 60%、有内存上限和背压的默认池，不加入新的高并发默认值。本文区分历史尝试与当前原生诊断，不把旧记录包装成本轮完整 A/B。

## 问题与假设

大站可能同时出现 DEV 推进缓慢、空闲 Worker 和长队列。候选假设是计算并行不足，提高池大小可以缩短基础表示时间。

这个假设只有在 CPU 计算槽不足、下游能及时消费且内存有余量时才成立。空闲 Worker 本身不能证明应增加并发；共享 gate、来源亲和、未消费输出、模板准入和内存压力都可能限制派发。

## 已尝试的路线及证据边界

[性能基线](../performance.md) 保留了此前把 Worker 比例从约 60% 提高到约 90% 的尝试：substation01 观测窗口中的推进由 225/285 降至 81/285，因此回退。原记录没有给出可复现的完整环境、固定观察时长和三次冷暖原始矩阵，不能从这两个计数推导精确加速比，也不能断言所有机器提高并发都会退化。

当前代码在 `desktop/src/services/devGeometryWorkerClient.ts` 中仍使用约 60% 的自动策略，并受内存上限、IFC 期间编译槽及输出背压约束。构建代码未恢复上述高比例默认值。

## 本轮大站观察

2026-10-23 使用独立原生验收应用、全新 WebView profile 和未登记该源的验收数据库打开 B1-1。构建源码指纹 `d40d54143f4fc30d347938744ed242a780ffb2cd10f870bdbb6dbc0a7eb04135`，EXE SHA-256 `760d9cd65a75a43a7f48b959c50fc580f5df12ae699af06220c45dae89e68a8a`。这次运行没有提高 Worker 数量，属于默认策略诊断，不是新一次高并发 A/B。

原始记录位于本地 `output/acceptance/stations/2026-10-23T01-00-26.388Z/`，其中 `session.json` 校验独立原生数据库路径，`samples.jsonl` 保存连续队列与进度，`benchmark-1.json` 为中途快照，`benchmark-2.json` 为基础表示完成后的阶段和资源快照。该目录由 Git 忽略，报告不包含原始工程数据。

在阶段快照中可以确认：

- IFC 尚在加载时 DEV 已推进至数千个 occurrence；compile 槽受限期间空闲 Worker 仍执行 bounds，没有复现旧的 DEV 0/0 长时间等待。
- 输出结果可达到 14 项的计数背压阈值，而字节总量仍小于 1 MiB。此时即使存在空闲 Worker，也不能直接归因为编译 gate 未释放。
- 缓存待写曾超过 2500 项；完成快照中几何/目录写入队列单项最大等待约 301 / 351 秒，模板队列约 370 秒。2617 个编译任务的 Worker 单项墙钟最大约 484 ms。这些是阶段墙钟与排队信息，不能相加为全站时间或视作 CPU 时间。
- 进程树私有内存峰值已达约 6.13 GiB。内存压力触发过空闲 Worker 回收，随后按既有策略恢复计算容量。

这些证据否定了“看到空闲 Worker，就应直接提高并发”这一决策依据。它们尚不足以证明哪个下游阶段独占全部耗时，仍需通过固定构建、逐阶段对照定位；不能据此未经实验就重写调度或批量缓存协议。

## 回退与保留范围

高 Worker 比例默认路线保持回退，不新增并行解析池，不放宽输出/输入预算，不将默认开关留作未验证的用户选项。现有诊断、gate 唤醒、bounds 回退和超时隔离继续保留；它们承担可观测性及局部故障恢复，不宣称提高线程数的性能收益。

本轮未尝试关闭 GPU、关闭沙箱或修改系统权限；原生启动目录问题与 DEV 性能判断分别记录。

## 重新尝试的条件

只有在默认路径的完整快照显示计算槽持续饱和、下游消费无积压、内存留有余量时，才重新测试并发参数。对照须使用同机、同源、同一构建和等价冷缓存，记录基础表示、当前视图、交互延迟、失败及内存。局部吞吐增长若伴随首屏、交互、内存或总完成时间退化，不能作为默认采用理由。
